# Blueprints System Reference

## Directory Layout

```
~/blueprints/                    # Separate git repo + Obsidian vault
└── <project>/                   # One dir per project (derived from git root)
    ├── spec/                    # Target-state specifications
    │   └── YYYYMMDD-<slug>.md
    ├── plan/                    # Implementation plans (linked to specs)
    │   └── YYYYMMDD-<slug>.md
    ├── review/                  # Code review findings
    │   └── YYYYMMDD-<slug>.md
    ├── report/                  # Post-implementation summaries
    │   └── YYYYMMDD-<slug>.md
    ├── docs/                    # Permanent reference docs (architecture, guides)
    └── archive/                 # Consumed artifacts from all types
```

## Artifact Frontmatter

Every artifact has YAML frontmatter generated by `ct create`:

```yaml
---
topic: "Add webhook retry logic"
created: "2026-04-06T14:30:00Z"
source: "[[20260405-webhook-spec]]"       # Optional: parent artifact
tags:
  - type/plan                              # Auto: artifact kind
  - project/my-service                     # Auto: from project path
  - domain/webhooks                        # User-supplied via --tags
  - stage/implementing                     # User-supplied via --tags
---
```

### Auto-Derived Tags

Always added by `ct create` — never pass these manually:
- `type/spec`, `type/plan`, `type/review`, `type/report`
- `project/<name>` — derived from project path, handles `.git` dirs and worktrees

### User-Supplied Tags

Pass via `--tags "domain/webhooks,stage/research"`:
- `domain/<area>` — combat, lua, ui, network, webhooks, auth, etc.
- `stage/<phase>` — research, implementing, shipped, stale
- Freeform tags accepted

### Permanent Docs

Files in `docs/` use `type/doc` tag. These are reference documents (architecture guides, API docs) — not workflow artifacts. They don't follow the artifact lifecycle.

## Project Name Derivation

`ct` determines the project name from the git root:
1. If path contains `.git` → extract project name (handles worktrees — all worktrees share name)
2. Otherwise → final path component
3. Fallback: `(no project)`

Always pass `--project "$(git rev-parse --show-toplevel)"` to ensure correct detection.

## Obsidian Integration

The blueprints repo is an Obsidian vault. Cross-reference artifacts using wiki-links.

### Link Syntax

- **Frontmatter source:** `--source "<stem>"` → adds `source: "[[stem]]"` 
- **Body references:** `[[stem]]` anywhere in markdown body
- **Stem** = filename without extension or path (e.g., `20260405-webhook-spec`)

### Finding Related Artifacts

```bash
ct vault related --project "$(git rev-parse --show-toplevel)" "<topic>"
```

Returns artifacts with overlapping keywords. If non-empty, append a `## Related` section to your artifact:

```markdown
## Related

- [[20260401-auth-overhaul]]
- [[20260403-session-tokens]]
```

### Vault Operations

```bash
ct vault check              # Find unresolved wiki-links (Obsidian CLI)
ct vault search "<query>"   # Full-text search (Obsidian CLI)
```

## Lifecycle

1. **Create** — `ct <type> create` writes file, commits, pushes
2. **Read/List** — `ct <type> read|list|latest|show` for discovery
3. **Consume** — workflow skills (`/develop`, `/review`) read artifacts
4. **Archive** — `ct <type> archive` moves to `archive/`, stores in git notes
5. **Prune** — `ct <type> prune --days N` auto-archives old artifacts

## Utility Commands

```bash
ct tool slug "Some Topic"           # → some-topic (URL-safe)
ct tool phases <plan-file>          # Parse **Phase N:** markers
ct tool gitcontext                  # Summarized git context for artifacts
ct vault init                   # Initialize ~/blueprints/ repo
ct vault migrate                # Migrate from legacy ~/.claude/ locations
```
